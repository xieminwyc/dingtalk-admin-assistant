## 1. 文档定位与范围

这份文档不再只是一次性的交互优化记录，而是首页工作台的唯一主规格。它要同时回答 3 个问题：

1. 首页为什么这样设计
2. 当前已经做到哪一层
3. 下一步应该按什么顺序继续做

### 1.1 文档用途

- 给未来继续开发的自己一个稳定的判断基线，避免重复讨论已经做过的设计选择
- 让产品语言和代码结构可以互相映射，降低“看文档像产品稿、看代码像另一套系统”的割裂感
- 把已上线、待完善、远期演进分层记录，便于后续拆任务和回溯决策

### 1.2 本文档覆盖范围

- 首页门户的信息架构与视觉定位
- 卡片、模式面板、输入框、聊天区的关键交互状态
- 首页五张能力卡与后端 `entryMode` / router / provider 的映射关系
- 当前已完成能力、P0 下一步、后续演进模块
- 验收标准、异常处理、测试关注点

### 1.3 本文档不覆盖的范围

- 完整企业级 Agent 平台全景设计
- 后台 CMS、知识运营平台、权限后台
- 真实图片生成服务接入细节
- 钉钉组织架构、审批流、统一身份体系的完整产品设计
- 独立移动端 App 的专门交互规范

### 1.4 维护规则

后续每次首页相关功能落地后，应优先更新本文件，而不是新开平行 spec。建议按以下原则维护：

- 已完成功能：更新到“当前已完成”
- 确认进入近期开发：移动到“P0 下一步”
- 暂不做但明确保留方向：记录到“后续演进模块”
- 原有旧 spec 保留作历史背景，不再继续扩展为主文档

## 2. 产品目标与非目标

### 2.1 产品目标

首页的核心定位不是传统聊天页，也不是纯导航页，而是一个“门户 + 对话工作台”。

本阶段首页需要达成的目标如下：

1. 降低空白页焦虑  
   用户打开页面时，不必先想 Prompt，而是能直接从高频入口开始。

2. 显性化高频办公任务  
   将“找制度 / 找对接人 / 找流程 / 帮我写作 / 图片生成占位”产品化为可见卡片，而不是隐藏在对话能力里。

3. 保持同页完成体验  
   用户发起任务后，不跳到另一页或另一个系统，而是在同一页面内完成模式选择、问题编辑、发送和查看回复。

4. 让入口模式与后端能力真正对齐  
   卡片不是营销文案，而是前端状态、请求协议和后端路由的轻量入口。

5. 为后续扩展保留结构  
   首页当前只做一个稳定的工作台骨架，但结构上要能自然演进到历史记录、垂直频道、更多同事 Agent 和结构化结果。

### 2.2 非目标

以下能力不属于当前首页 P0 的完成定义：

- 做成一个完整的多 Agent 平台
- 在首页直接实现真实图片生成结果流
- 实现全量历史中心与复杂会话管理
- 做复杂的角色市场、插件市场、运营后台
- 为每个业务领域都创建独立二级页面和专属工作台

## 3. 当前已完成

这一节记录仓库中已经落地、可作为后续开发起点的能力。

### 3.1 页面与结构

- `/` 已切换为正式首页工作台，采用 `home / drilldown / chat` 三态主画布
- 顶部左上角提供历史记录触发按钮，点击后从左侧展开抽屉，而不是常驻侧栏
- 底部输入区常驻，不随首页、模板页、对话页切换而消失
- `/debug` 继续保留为调试入口，正式体验与开发调试保持分离

### 3.2 首页入口与 drilldown

- 首页固定展示五张卡片：`找制度`、`找对接人`、`找流程`、`图片生成`、`帮我写作`
- 整张卡片点击后进入对应的 `drilldown` 专家模式，而不是直接发送
- 首页卡片上的示例问题仍只做填充，不自动发送，保留用户改写空间
- `drilldown` 已由 `home-config` 的 `templates` 驱动，支持标题 + prompt 双层文案
- `image_placeholder` 在 `drilldown` 中会明确展示“尚未上线，但可先整理提示词”的占位说明

### 3.3 会话连续性与历史抽屉

- 前端本地维护 `sessionId`、消息列表和轻量会话摘要
- 历史抽屉当前展示最近会话摘要和 `开启新话题`
- 已支持刷新后恢复当前会话的基础消息内容
- `开启新话题` 会回到首页工作台，清空当前草稿和消息状态

### 3.4 聊天结果与反馈状态

- 用户消息发送后会立即进入消息流
- 助手会先出现“思考中”气泡和打点动画，再替换成正式回复
- `chat` 已支持基础分层结果渲染：结构化段落、来源区块、模式徽标
- 当前知识类回复可从文本结构中抽出“依据来源”并单独展示
- 请求失败时前端会显示友好错误信息，而不是无反馈失败

### 3.5 前后端能力映射已接通

- 首页请求继续通过 `/api/dingtalk/webhook` 发送 `entryMode`
- `entryMode` 已进入 assistant runtime、intent analyzer 和 request router
- `image_placeholder` 已有后端保底回复
- `contact` 已支持优先走联系人目录解析
- `writing` 已支持在启用 response generator 时增加企业写作提示
- knowledge resolution 已为后续来源链接保留 `sourceUrl` 字段边界

### 3.6 当前测试基础

- 首页测试已覆盖三态流转、历史抽屉、模板化 drilldown、图片占位态、思考态与发送链路
- `/debug` 页面测试已覆盖关键调试字段渲染与调试请求发送
- webhook route 测试已覆盖 debug 契约、entryMode 透传与空消息校验
- assistant service、router、knowledge / task / contact 等核心模块已有测试

## 4. P0 下一步

这一节不是零散 todo，而是首页继续开发时的近期模块顺序。只有进入近期迭代的内容才放在这里。

### 4.1 工作台壳层升级

下一阶段首页不再继续沿用“所有内容都堆在同一画布”的单态结构，而是升级为更明确的工作台壳层。推荐采用：

- 顶部栏：左上角保留轻量历史入口按钮、品牌名、当前状态提示、`新话题` 入口
- 主画布：使用 `home / drilldown / chat` 三态切换
- 底部输入区：常驻固定，不随主画布状态改变而消失
- 历史记录：默认收起，通过左上角入口按钮展开为左侧抽屉

历史记录不采用常驻大侧栏，原因如下：

- 比常驻侧栏更克制，不会压缩首页首屏卡片和内容空间
- 比完全没有历史入口更像“持续助手”
- 与当前项目从单页工作台逐步演进的路径更兼容

本阶段对历史抽屉的要求：

- 默认收起
- 点击左上角入口后，从左侧滑出
- 桌面端宽度控制在约 `240px - 280px`
- 移动端采用覆盖式抽屉
- 只展示最近 `5 - 10` 条会话摘要和 `开启新话题`
- 不在本阶段实现搜索、分类、批量删除

### 4.2 模式化回复呈现

当前首页已经有模式入口，但回复区仍主要是统一文本气泡。下一步应优先补强“入口模式感”和“结果可读性”的一致性。

建议目标：

- `knowledge` 回复中更明确展示来源、适用范围、推荐继续追问方向
- `task` 回复中更突出办理入口、办理前准备、可用性状态
- `contact` 回复中更突出联系人、团队、建议动作
- `writing` 回复中更像可直接复用的成稿，而不是普通闲聊答复

这一步不要求一开始就上复杂卡片 UI，但至少要先完成回复模板和信息层级的标准化。

### 4.3 会话连续性最小增强

首页当前有本地 `sessionId` 和日志上下文，但用户层面还没有明确的“可回看、可继续”的体验。

P0 建议先做最小连续性增强：

- 首页刷新后尽量保持当前会话上下文
- 保持最近一段消息的可回看性
- 明确“新话题”与“延续当前话题”的行为边界

这一阶段先不做完整历史中心，但要把左侧历史抽屉需要的基础数据路径理顺。

### 4.4 首页内容维护与真实性

首页现在依赖 `home-config` 和样例数据，后续需要提升“入口文案”和“实际能力”之间的一致性。

近期要补的重点：

- 统一五张卡的文案风格，减少 demo 感
- 样例问题要与真实可回答内容对齐
- 快捷标签与后端可命中的数据范围保持一致
- 同事们区域和快捷链接明确哪些是展示位，哪些是未来真实入口

### 4.5 移动端与可访问性校验

当前 spec 已经要求兼容移动端，但还需要把它从“设计要求”落成“实际校验项”。

近期至少要验证：

- 卡片和模式面板在窄屏下是否仍可读、可点
- 输入区、发送按钮、聊天消息在移动端是否保持稳定布局
- 键盘与可聚焦行为是否符合基础可访问性预期

### 4.6 文档与代码同步机制

既然本文件被定义为主规格，后续每完成一次首页迭代，都需要同步写清楚：

- 哪些交互已经落地
- 哪些仍在规划中
- 哪些能力被推迟或降级

否则文档会再次退化成“某次讨论记录”，失去追溯价值。

## 5. 关键交互设计

这一节描述首页工作台的核心状态机，目标是让“页面怎么动”和“代码怎么承接”保持一致。

### 5.1 页面骨架

下一阶段首页采用四层结构：

1. 顶部栏  
   左侧为历史抽屉入口按钮，中间或左侧为品牌与当前状态说明，右侧保留 `新话题` 或等效重置入口。

2. 左侧历史抽屉  
   默认隐藏，点击后展开；其职责是承载最近会话，而不是变成新的主导航系统。

3. 主画布  
   负责三态内容切换：
   - `home`：门户首页和业务卡入口
   - `drilldown`：某一模式下的模板引导页
   - `chat`：正式消息流与结果承接区

4. 底部固定输入区  
   无论当前是 `home`、`drilldown` 还是 `chat`，输入区都保持可见，避免用户切状态后失去输入能力。

### 5.2 状态总览

| 状态 | 触发方式 | 前端表现 | 系统行为 |
| --- | --- | --- | --- |
| `home` | 首次进入首页或结束新话题后 | 展示欢迎区、业务卡、轻量说明与默认输入提示 | 不主动发请求 |
| `history_open` | 点击左上角历史入口 | 左侧抽屉滑出，主画布保持当前状态或轻微位移 | 不主动发请求，只读取本地或内存中的最近会话摘要 |
| `drilldown` | 点击某张业务卡 | 进入对应模式的二级引导页，显示模板建议和更明确的模式说明 | 仅记录 `activeEntryMode`，不自动发送 |
| `prefill` | 点击模板、示例问题或快捷标签 | 文本进入输入框，可继续编辑 | 不发请求，保留当前模式 |
| `chat` | 用户发送成功后 | 主画布切换为消息流，保留模式信息和输入区 | 携带 `entryMode` 发起请求 |
| `replying` | 请求进行中 | 消息流展示思考态，输入区禁用 | 等待接口返回 |
| `error_or_clarify` | 接口失败或未命中 | 友好错误、澄清或保守兜底文案出现在消息流中 | 页面不重置，允许继续追问 |

### 5.3 交互规则

#### A. 点击左上角历史入口

- 作用：打开最近会话抽屉
- 结果：左侧抽屉滑出，展示最近会话摘要和 `开启新话题`
- 再次点击入口或点击遮罩后收起
- 当前阶段不在抽屉中承担复杂管理动作

#### B. 在 `home` 态点击业务卡

- 作用：进入某种专家模式的二级引导页
- 结果：主画布进入 `drilldown`，而不是直接进入对话流
- 输入区继续保留，用户可以直接输入，也可以先选模板

#### C. 在 `drilldown` 态点击模板

- 作用：提供更接近结果的起始 Prompt
- 结果：优先填充输入框，并可按具体设计选择直接发送或等待用户确认
- 推荐默认仍保留“可编辑后发送”的控制权，避免误发

#### D. 手动输入并发送

- 作用：真正发起本轮请求
- 结果：主画布进入 `chat`，前端提交 `sessionId + entryMode + text.content`
- 后端仍可根据 analyzer 结果纠偏，避免前端模式把对话锁死

#### E. 开启新话题

- 作用：清空当前工作上下文，回到首页
- 结果：生成新会话，主画布回到 `home`
- 历史抽屉中保留旧会话摘要，但不要求当前阶段实现复杂多会话切换

### 5.4 核心设计原则

- 入口模式是引导，不是强制锁定
- 用户先编辑，再发送，优先降低误触成本
- 首页保持“轻门户 + 可连续对话”平衡，不做重聊天产品的复杂操作流
- 历史能力优先做成轻抽屉，而不是先上重侧栏
- `drilldown` 的价值是帮助用户收敛问题，而不是增加点击路径
- 每次交互都要让用户清楚自己当前在哪种模式下工作

### 5.5 `chat` 视图结果层级

`chat` 视图不应退化成普通 IM 式消息堆栈，而应承担“对话流 + 结果承接区”的双重职责。

每条助手消息建议按以下三层组织：

1. 正文  
   优先展示对用户最有用的自然语言回答。

2. 结果补充区  
   按 `entryMode` 或 resolution 类型展示附加信息：
   - `knowledge`：来源、适用范围、推荐继续追问
   - `task`：办理入口、办理前准备、可用性提示
   - `contact`：联系人、团队、建议动作
   - `writing`：优先保留成稿正文，不强行塞入过多碎信息

3. 轻量 mode 标识  
   允许用弱化标签提示当前结果属于 `KNOWLEDGE`、`TASK`、`CONTACT` 或 `WRITING`，但不应压过正文。

### 5.6 citation / 来源展示

来源信息应比一行灰字更清楚，但不需要在本阶段引入复杂卡片系统。

建议展示方式：

- 放在助手消息下方
- 使用单独的“依据来源”区块
- 每条来源显示 `documentTitle`
- 有链接时允许点击跳转；无链接时只展示标题

这样可以兼顾可信度、扫读效率与实现复杂度。

### 5.7 错误态、澄清态与占位态

`chat` 视图至少应区分以下三类非成功结果：

1. 系统错误  
   请求失败、超时或服务异常。  
   要求：明确告诉用户失败了，但保留继续输入能力。

2. 未命中 / 澄清  
   问题模糊或知识未命中。  
   要求：优先引导用户换关键词、补充信息或使用 related keywords，而不是机械报错。

3. 占位能力  
   如 `image_placeholder`。  
   要求：明确说明该能力尚未上线，并提示当前可提供的替代帮助，例如整理提示词。

### 5.8 历史抽屉摘要规则

历史抽屉本阶段只做轻量会话摘要，不做 AI 自动总结。

建议每条摘要至少包含：

- `sessionId`
- 标题：优先取该会话第一条用户消息的前 `18 - 24` 个字
- `updatedAt`
- 是否为当前会话

补充规则：

- 如果第一条用户消息过短，可退回使用最近一条用户消息
- 当前阶段不做搜索、标签、分组和批量管理
- 历史抽屉的角色是“会话切换器”，不是“完整历史中心”

### 5.9 组件边界与状态字段

下一阶段建议把当前首页从单文件状态提升为更清晰的工作台边界。

推荐组件职责如下：

- `HomeShell`：整体布局、主状态编排、抽屉开关、当前会话选择
- `HistoryDrawer`：最近会话摘要与 `开启新话题`
- `HomeCanvas`：首页欢迎区、业务卡、同事们、快捷入口
- `DrilldownCanvas`：模式头部、模板列表、返回首页
- `ChatCanvas`：消息流、citation、思考态、错误态、mode 标签
- `Composer`：输入框、placeholder、发送按钮

推荐主状态字段如下：

```ts
type HomeView = "home" | "drilldown" | "chat";

type ConversationSummary = {
  sessionId: string;
  title: string;
  updatedAt: number;
  isCurrent?: boolean;
};

type ChatEntry = {
  id: string;
  role: "user" | "assistant";
  content: string;
  mode?: EntryMode | null;
  isThinking?: boolean;
  isError?: boolean;
  citations?: {
    documentTitle: string;
    sourceUrl?: string;
  }[];
  meta?: {
    title?: string;
    scope?: string;
    contactName?: string;
    team?: string;
    entry?: string;
    actionHint?: string;
  };
};
```

当前阶段无需一次性把所有字段都用满，但这些字段能够为 `chat` 视图保留结果补充区的承载位。

## 6. 能力映射与技术落点

首页上的每张卡都必须能对应到明确的代码路径，否则卡片只是文案壳子。

| 首页卡片 | `entryMode` | 当前后端落点 | 当前数据来源 | 当前状态 | 下一步方向 |
| --- | --- | --- | --- | --- | --- |
| 找制度 | `knowledge` | intent analyzer + request router + knowledge retriever | `docs/knowledge` 文档优先，样例知识卡兜底，可选外部 RAG | 可用，是当前最真实的核心能力 | 增强引用展示、相关问题建议、未命中兜底 |
| 找对接人 | `contact` | request router 优先联系人目录解析 | 本地联系人目录样例数据 | 可用，但仍偏种子数据 | 后续对接真实通讯录或更完整目录 |
| 找流程 | `task` | task catalog resolver | 本地事务目录样例数据 | 可用 | 强化结果结构化展示与入口显性化 |
| 帮我写作 | `writing` | 仍走对话生成链路，并在启用 response generator 时注入企业写作提示 | 模型直答 + resolution facts | 可用，但风格仍需要校准 | 提升模板感、成稿感、可编辑性 |
| 图片生成 | `image_placeholder` | router 直接返回占位回复 | 无真实图片服务 | 仅占位 | 后续接提示词辅助或真实出图链路 |

### 6.1 首页请求链路

当前首页请求链路可以概括为：

```text
首页交互
  -> 生成 sessionId / entryMode / text.content
  -> POST /api/dingtalk/webhook
  -> assistant runtime
  -> intent analyzer
  -> request router
      -> knowledge / contact / task / open_response / clarify
  -> response generator 或 reply builder
  -> 返回首页消息流
```

### 6.2 当前架构判断

现有架构已经满足首页继续演进的基本前提：

- 前端已有稳定状态承接点：`activeEntryMode`、`draft`、`messages`、`isSending`
- 后端已有稳定能力边界：analyzer、router、provider、reply builder
- 会话日志和上下文服务已存在，能支撑后续最小历史能力

因此后面继续做首页，不需要推翻架构，重点是补强展示层、结果层、视图层与会话层。

### 6.3 下一阶段前端状态建议

为了支撑三态工作台和抽屉式历史，前端至少需要补充以下状态：

- `view: "home" | "drilldown" | "chat"`
- `activeEntryMode: EntryMode | null`
- `isHistoryOpen: boolean`
- `draft: string`
- `sessionId: string`
- `messages: ChatEntry[]`
- `conversationSummaries: ConversationSummary[]`
- `isSending: boolean`
- `error: string | null`

其中：

- `HomeShell` 负责会话选择和主状态编排
- `HistoryDrawer` 只负责展示列表，不反向拥有整页导航逻辑
- `ChatCanvas` 不直接管理会话切换，只消费当前会话数据

## 7. 异常处理与测试关注点

### 7.1 异常处理原则

- 空输入不发送，减少无意义请求
- 接口异常时返回友好失败提示，而不是让用户看到静默空白
- analyzer 失效时走保守澄清，不冒险给错误答案
- 知识未命中时优先给换关键词或相关词提示
- 图片生成未上线时明确说明“尚未支持”，不伪造成功结果

### 7.2 测试关注点

后续首页迭代应至少覆盖以下测试层面：

1. 页面状态流转测试  
   验证 `home -> drilldown -> chat` 的切换是否正确，模板点击是否只预填不误发。

2. 历史抽屉测试  
   验证抽屉展开 / 收起、当前会话高亮、`开启新话题` 行为与会话切换逻辑。

3. `chat` 结果层级测试  
   验证 citation、mode 标签、错误态、澄清态、占位态是否按不同类型正确呈现。

4. 模式与请求协议测试  
   验证不同 `entryMode` 是否被正确带入请求体，并在后端链路中生效。

5. 路由与回复测试  
   验证 knowledge / contact / task / open_response / clarify 的分流是否符合预期。

6. 回归测试  
   每次改首页交互时，都需要确认没有破坏原有聊天链路和 `/debug` 调试入口。

---

## 8. 验收标准

首页主工作台在当前阶段可以视为“稳定可继续开发”，需要至少满足以下标准：

1. 首页默认进入 `home`，展示门户入口，而不是直接压成聊天页
2. 点击业务卡后进入 `drilldown`，而不是直接跳入消息流
3. 模板点击后默认预填输入框，用户仍可修改后再发送
4. 发送后进入 `chat`，并保留当前模式语义
5. 左上角历史入口可展开抽屉，抽屉默认收起
6. 历史抽屉只承担最近会话回看和 `开启新话题`，不做复杂管理
7. assistant 回复在 `knowledge / task / contact / writing` 下具备不同信息层级
8. citation、错误态、澄清态、占位态都能被明确区分
9. 移动端下历史抽屉、主画布、输入区不会互相挤坏
10. `/debug` 仍能观察首页模式带来的路由和回复差异
11. 允许视觉样式继续迭代，但不得破坏三态结构、历史抽屉入口、固定输入区和模式化回复层级

## 9. 后续演进模块

这一节只记录中后期方向，粒度到模块，不展开到完整交互稿。

### 9.1 历史记录模块

价值：

- 让首页从“单次工作台”升级为“可回访的持续助手”
- 支撑“新话题”和“继续当前话题”的明确分界

边界：

- 初期采用“左上角入口 + 左侧抽屉”的轻量方案
- 不需要一开始就做复杂搜索、标签、批量管理

### 9.2 垂直频道模块

价值：

- 把高频复杂场景从通用模式进一步沉淀成专业入口
- 例如制度查询专家、工程验收查询、流程专家等

边界：

- 当前首页先落地 `home / drilldown / chat` 三态，不直接切入完整频道页
- 未来可在命中率和内容成熟后，再扩展为更强的专属工作台

### 9.3 权限与知识隔离模块

价值：

- 保证不同用户只能看到自己有权限访问的制度和资料
- 为后续企业级接入打基础

边界：

- 当前阶段先保留架构意识，不在首页层直接实现复杂权限系统
- 真正落地时应在 retriever / provider 层完成，不把权限逻辑写死在 UI 层

### 9.4 结构化结果模块

价值：

- 让 `task`、`contact`、`knowledge` 的结果更像“可执行信息”而不是纯文本
- 提升扫读效率和操作引导能力

边界：

- 可从轻量信息块开始，而不是一开始就构建复杂卡片系统
- 首页先保证信息层级正确，再逐步强化视觉组件

### 9.5 同事们与多 Agent 扩展模块

价值：

- 让首页从单助手扩展为多助手协作入口
- 为日程助理、律政助手、流程助手等角色化能力预留空间

边界：

- 当前“同事们”区域主要是展示位，不承诺复杂切换逻辑
- 后续是否独立成多 Agent 中枢，应以真实使用场景决定，而不是先做概念堆叠

### 9.6 文件上传与多模态输入模块

价值：

- 支持用户提交附件、图片、截图，减少纯文本描述成本
- 对制度检索、写作润色、图片生成等都具有增强价值

边界：

- 当前首页输入区仍以文本为主
- 后续接入时要同时考虑上传协议、文件安全和结果展示方式

## 10. 当前结论

首页工作台当前已经具备一个可持续演进的基础骨架：

- 产品定位已经从“调试聊天页”转为“门户 + 对话工作台”
- 前端入口交互和后端能力路由已经基本对齐
- 下一阶段正式选定“三态工作台 + 抽屉式历史入口”的演进路线
- 现阶段最重要的不是继续扩范围，而是把回复层、会话层、内容真实性和移动端体验补扎实

后续开发应默认以本文件为首页唯一主规格。若出现新想法，优先判断它属于：

- 已经落地：写进“当前已完成”
- 近期开发：写进“P0 下一步”
- 未来方向：写进“后续演进模块”

只有这样，这份文档才会真正成为可追溯、可开发、可持续维护的蓝图，而不是一次性的讨论记录。

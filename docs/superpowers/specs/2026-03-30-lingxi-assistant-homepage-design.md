# 灵犀助手首页与同页工作台 MVP 设计

> 日期：2026-03-30
> 范围：灵犀助手首页重构与同页工作台 MVP
> 目标：将当前“网页调试聊天页”升级为贴近“万事通”参考图的正式 H5 门户，并让首页承载制度查询、对接人查询、流程办理、写作辅助与后续图片生成入口。

## 1. 设计目标

当前首页仍是开发调试用途的聊天工作台，重点在于查看 `debug` 元信息，而不是面向员工的正式入口。这与产品目标存在明显偏差：

1. 缺少“门户首页”感，打开后更像内部测试页
2. 入口结构过于技术化，员工无法快速理解“我可以在这里做什么”
3. 没有把“找制度 / 找对接人 / 找流程 / 图片生成 / 帮我写作”这五类需求显式产品化
4. 对话能力存在，但没有和首页推荐问题、业务入口形成自然联动
5. 调试能力与正式体验混在同一路径，不利于后续上线和持续开发

本次 MVP 的目标是：

1. 首页替换为正式 H5 门户，视觉尽量贴近用户提供的“万事通”参考图
2. 建立五张业务卡入口，让用户一眼知道机器人可以处理哪些事情
3. 保留“同页继续对话”的体验，点击卡片或示例问题后不跳页
4. 让不同入口真的对应不同能力，而不是只有不同按钮文案
5. 将调试能力迁移到单独路由，保留开发效率同时不污染正式首页

## 2. 视觉与交互定位

### 2.1 视觉主方向

首页主视觉采用用户确认的 `A` 方向，即更接近第一张“万事通”参考图：

- 使用白底页面与轻阴影卡片
- 顶部采用“左侧头像 / Logo + 右侧欢迎语与介绍文案”的品牌式头部
- 不采用大面积蓝色 Hero 作为主结构
- 卡片图标使用轻量点缀色，保持企业 H5 的简洁和稳定
- 页面整体克制、清爽，避免自行发挥为另一套完全不同的营销风格

### 2.2 核心体验定位

首页不是单纯导航页，也不是纯聊天页，而是“门户 + 对话工作台”的混合结构。

用户应当可以在一个页面内完成：

1. 看到助手身份和能力说明
2. 通过业务卡快速进入不同能力
3. 点击示例问题直接发起对话
4. 在同页下半部分持续与助手对话

## 3. 页面信息架构

首页结构从上到下分为五个区域：

### 3.1 顶部欢迎区

- 左侧为万事通头像或品牌图标
- 右侧为动态欢迎语，例如“早上好，黄鹏，我是万事通”
- 欢迎语下方展示一段能力说明，强调：
  - 可查制度
  - 可找对接人
  - 可找流程
  - 可辅助写作
  - 后续支持更多办公场景

该区域要传递“这是一个正式企业助手”的第一印象。

### 3.2 业务卡片矩阵

首页固定展示五张业务卡：

- `找制度`
- `找对接人`
- `找流程`
- `图片生成`
- `帮我写作`

每张卡包含：

- 标题
- 辅助说明
- 一条示例问题

点击卡片本身与点击示例问题的行为不同：

- 点击卡片：激活当前模式，并将焦点引导到输入区
- 点击示例问题：直接发送该问题，并进入对应处理链路

### 3.3 同事推荐区

业务卡下方展示“万事通的同事们”或等效标题的推荐区。

首版先放 2 到 3 个常用角色入口，例如：

- 日程助理
- 律政助手
- 查询状态

该区域主要承担“扩展能力展示”和“后续角色化助手入口”的产品空间，不要求本次做复杂逻辑。

### 3.4 快捷入口区

推荐区下方可保留轻量快捷入口条，用于承载：

- 高频业务入口
- 常用系统链接
- 教程或操作视频

首版允许使用静态配置，不要求复杂个性化。

### 3.5 底部常驻对话区

首页底部保留一个大输入区与聊天记录区。

设计目标：

- 打开首页时保持轻量空态，不要一上来就压成重聊天界面
- 一旦用户点击卡片、示例问题或手动发送消息，对话区自然承接当前动作
- 不跳转到独立聊天页，保持工作台体验连续

## 4. 五张卡的能力映射

本次 MVP 前台展示五张卡，后台对应五种处理模式：

### 4.1 找制度

`找制度` 明确映射到内部知识检索能力。

处理方式：

- 优先走内部知识库检索链路
- 复用当前 `internal_knowledge` 路由能力
- 命中后返回答案、适用范围与来源提示
- 未命中时返回保守澄清或建议换关键词

这是本次 MVP 中最“真实可用”的核心能力之一。

### 4.2 找对接人

`找对接人` 首版不接真实钉钉组织架构，而是使用本地联系人目录。

处理方式：

- 新增本地联系人目录数据
- 通过关键词匹配或轻量解析，返回联系人、职责说明和建议动作
- 例如“PMS 制卡问题应该找谁处理” -> 返回对应对接角色与说明

该方案能快速提供可用体验，同时为后续接钉钉通讯录预留边界。

### 4.3 找流程

`找流程` 映射到事务目录与办理入口能力。

处理方式：

- 复用当前 `task catalog` 能力
- 返回办理入口、准备材料、可用性与兜底联系人
- 回复风格以“带用户到正确入口”为主，而不是长篇解释规则

### 4.4 图片生成

`图片生成` 首版只做占位能力，不接真实出图服务。

处理方式：

- 用户从该卡进入时，返回友好的“即将支持”提示
- 可以顺带提示：后续将支持根据主题和风格生成图片
- 不在本次 MVP 内接入真实图片接口或图片渲染结果

该设计保证首页入口完整，同时控制实现范围。

### 4.5 帮我写作

`帮我写作` 映射到写作型 LLM 回复模式。

处理方式：

- 继续使用模型直答能力
- 通过入口模式或提示词，将回复风格调整为更适合企业写作
- 支持方案、汇报、通知、周报、总结等内容生成

该模式要和普通闲聊区分开，让用户感觉“这是专门帮我起草内容”的入口。

## 5. 同页对话交互

### 5.1 模式激活

首页交互采用“入口模式 + 后端兜底”的方式。

规则如下：

- 用户点击卡片时，前端记录当前模式
- 用户点击示例问题时，前端直接带该模式发送请求
- 用户在输入区手动输入时，优先沿用当前模式
- 后端仍保留意图分析与路由兜底，避免因为入口模式导致后续追问被错误锁死

这保证了：

1. 首页入口具有明显的产品模式感
2. 多轮对话仍保留纠偏能力

### 5.2 空态

默认空态应保持轻量，例如：

- “有问题尽管问我～”
- “你可以问制度、找流程、找对接人，或者让我帮你写作”

空态目标是鼓励用户发起第一轮，而不是展示技术信息。

### 5.3 发送与思考态

发送后采用“伪流式体验”作为首版实现：

1. 用户消息立即进入对话区
2. 助手先出现“AI 正在思考...”气泡
3. 接口返回后，再替换为正式回复

这样能满足 PRD 中“思考态”的要求，同时避免本次 MVP 直接重做完整流式协议。

### 5.4 错误态与未命中态

需要定义轻量异常反馈：

- 接口失败时，在对话区展示友好错误提示
- 知识未命中时，给出换关键词或联系人建议
- 流程未命中时，给出兜底联系人，而不是返回空白
- 图片生成功能未上线时，给出明确占位提示，而不是假装成功

## 6. 技术设计

### 6.1 首页与调试页分离

当前首页 `src/app/page.tsx` 为调试聊天页。本次改造后：

- `/` 变为正式灵犀助手首页
- 当前调试工作台迁移到单独路由，例如 `/debug`

目标是让正式体验与开发调试能力各司其职。

### 6.2 请求协议扩展

现有主请求入口继续复用 `/api/dingtalk/webhook`，首版不新开主业务接口。

前端请求增加轻量字段，例如：

```ts
type EntryMode =
  | "knowledge"
  | "contact"
  | "task"
  | "image_placeholder"
  | "writing";
```

扩展后的请求体可以是：

```ts
{
  sessionId?: string;
  debug?: boolean;
  entryMode?: EntryMode;
  text: {
    content: string;
  };
}
```

设计原则：

- 前端通过 `entryMode` 表达“这句话是从哪个入口发起的”
- 后端优先参考 `entryMode`
- 仍保留现有 analyzer 作为兜底，避免模式绑定过死

### 6.3 新增联系人目录边界

为 `找对接人` 新增联系人目录模块，建议结构如下：

```ts
type ContactDirectoryItem = {
  id: string;
  title: string;
  keywords: string[];
  contactName: string;
  team?: string;
  description: string;
  actionHint?: string;
};
```

首版允许使用静态种子数据，后续可替换为：

- 钉钉组织架构查询
- 数据库表
- 外部目录服务

### 6.4 写作与图片占位模式

`帮我写作` 与 `图片生成` 不要求新建完整 provider，但要在路由或回复生成层支持入口模式的差异化处理：

- `writing`：让回复生成更偏成稿和企业文风
- `image_placeholder`：直接给出固定占位回复或轻量 resolution

### 6.5 前端状态设计

首页至少需要维护以下状态：

- `activeEntryMode`
- `messages`
- `draft`
- `isSending`
- `isThinking`
- `error`
- 推荐卡片配置与推荐角色配置

同时需要支持：

- 点击卡片激活模式
- 点击示例问题直接发送
- 输入框聚焦与发送
- 回复落入同页聊天区

## 7. MVP 范围控制

### 7.1 In Scope

- 正式首页替换当前调试页
- 调试页迁移到独立路由
- “万事通”风格头部
- 五张业务卡完整展示与点击交互
- 同页对话区
- `找制度` 知识检索接通
- `找流程` 事务目录接通
- `找对接人` 本地联系人目录接通
- `帮我写作` 写作模式接通
- `图片生成` 占位提示接通
- “AI 正在思考...”思考态

### 7.2 Out of Scope

- 真实图片生成服务
- 接入钉钉真实通讯录与组织架构
- 完整流式输出协议
- 个性化推荐算法
- 复杂多轮表单收集
- 首页运营后台

## 8. 验收标准

本次 MVP 完成后，应满足以下验收标准：

1. 打开首页后，看到的是正式灵犀助手门户，而不是调试聊天页
2. 顶部头部视觉贴近“万事通”参考图的结构与气质
3. 五张业务卡完整可见，卡片内示例问题可直接发送
4. 点击卡片后，不跳页，而是在当前页进入对话
5. `找制度` 可以命中知识库并返回制度答案
6. `找流程` 可以返回事务入口或办理说明
7. `找对接人` 可以返回本地联系人目录结果
8. `帮我写作` 可以输出可用的企业写作文案
9. `图片生成` 会明确提示“即将支持”或等效占位信息
10. 发送后会先展示“AI 正在思考...”状态
11. 原调试能力被迁移到独立路由，并且仍可继续使用

## 9. 风险与后续演进

### 9.1 首版风险

- `找对接人` 使用本地种子数据，覆盖范围有限
- `帮我写作` 若仅靠入口模式控制，写作稳定性仍依赖模型提示词
- `图片生成` 仅做占位，可能被部分用户理解为“功能未完成”
- 伪流式体验能满足思考态，但与真正 stream 仍有差距

### 9.2 后续演进方向

- `找对接人` 接入真实钉钉通讯录或组织架构
- `找流程` 对接真实 OA 或系统入口
- `图片生成` 接入真实图片服务
- 同页对话升级为真实流式输出
- 首页引入更细粒度的角色化助手与快捷推荐策略
